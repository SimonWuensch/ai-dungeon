# diagnosing-bugs

<SkillHeader category="On-Ramp" githubPath="diagnosing-bugs" />

**Für die harten Bugs** — den, der beim ersten Blick standhält, den seltenen Flake, die Regression, die sich zwischen zwei bekannt-guten Zuständen eingeschlichen hat. Verweigert sich jeder Theorie, bis ein **straffer Feedback-Loop** steht, der auf genau diesem Bug rot wird.

## Wann nutzen

- Der Nutzer sagt "diagnose das" / "debug das", oder meldet etwas als kaputt/wirft einen Fehler/ist langsam.

**Phase 1 ist der eigentliche Skill** — alles danach ist mechanisch. Ohne einen Befehl, der schon einmal lief und rot wurde, gibt es keine Phase 2. Erlaubte Wege zu einem Loop reichen von einem fehlschlagenden Test über ein Curl-Skript bis zum letzten Mittel, einem HITL-Bash-Skript für Schritte, die nur ein Mensch klicken kann.

Bei nicht-deterministischen Bugs zählt nicht ein sauberer Repro, sondern eine **höhere Reproduktionsrate** — bis sie hoch genug ist, um debuggbar zu sein.

## Gut zu wissen

Jeder Debug-Log trägt ein eindeutiges Tag (`[DEBUG-a4f2]`) — Cleanup am Ende wird damit zu einem einzigen `grep`.
