# tdd

<SkillHeader category="Hauptfluss" invocation="model" githubPath="engineering/tdd" />

**Der rot → grün-Loop — und die Referenz, die dafür sorgt, dass dabei Tests entstehen, die es wert sind, behalten zu werden.** Nicht nur "schreib zuerst einen Test", sondern was einen *guten* Test ausmacht, wo Tests hingehören und welche Fallen es zu vermeiden gilt.

## Wann nutzen

- Immer, wenn Verhalten testgetrieben gebaut werden soll — eigenständig, oder als Unterprogramm von `implement`.

## Wie es funktioniert

**Seams zuerst vereinbaren.** Ein Seam ist die öffentliche Grenze, an der getestet wird — niemals gegen Interna. Vor dem ersten Test werden die zu testenden Seams mit dem Nutzer abgestimmt: *"Was ist das öffentliche Interface, und welche Seams testen wir?"*

**Drei Anti-Pattern, auf die geachtet wird:**
- **Implementation-gekoppelt** — bricht bei Refactoring, obwohl sich das Verhalten nicht geändert hat.
- **Tautologisch** — die Erwartung wird genauso berechnet wie der Code selbst, kann also nie widersprechen.
- **Horizontal geschnitten** — erst alle Tests, dann alle Implementierung. Richtig ist die **vertikale Scheibe**: ein Test → eine Implementierung → wiederholen.

## Beispiel

Seam: die Funktion `shouldDeliverDuringQuietHours(event, quietHours)`. Ein Zyklus:

1. **Test schreiben:** "kritisches, unterdrückbares Event während stiller Zeit → `false`"
2. **Rot:** Die Funktion existiert noch nicht.
3. **Minimaler Code:** gerade genug, damit dieser eine Test grün wird.
4. **Grün.** Nächste Scheibe: "kritisches, nicht-unterdrückbares Event während stiller Zeit → `true`."

Jede Scheibe testet **eine** Regel, nie die ganze Logik auf einmal — das hält jeden Schritt klein und den nächsten roten Test aussagekräftig.

## Gut zu wissen

**Refactoring ist nicht Teil des Loops** — das gehört in die Review-Phase (`code-review`), nicht in den rot-grün-Zyklus selbst.
