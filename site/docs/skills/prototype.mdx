# prototype

<SkillHeader category="Hauptfluss" invocation="model" githubPath="engineering/prototype" />

**Wegwerfcode, der genau eine Frage beantwortet.** Kein Feature-Vorbau, kein Testfundament — ein Prototyp existiert nur, damit du (oder jemand ohne Entwicklungshintergrund) etwas Konkretes anfassen und beurteilen kann, bevor die echte Implementierung beginnt.

## Wann nutzen

- Als Umweg innerhalb von `grill-with-docs`, wenn eine Frage sich nicht mehr im Gespräch klären lässt.
- Immer wenn "fühlt sich dieser Zustandsautomat richtig an?" oder "wie soll das aussehen?" nur mit Anfassen zu beantworten ist.

## Regeln, die für beide Zweige gelten

- **Von Tag eins als Wegwerfcode markiert** — liegt nah am Zielort im echten Projekt, ist aber klar als Prototyp erkennbar benannt.
- **Trivial startbar**: ein Befehl, mehr nicht.
- **Keine Persistenz** außer die Frage betrifft explizit eine Datenbank — dann eine klar "PROTOTYPE, wipe me" markierte Scratch-DB.
- **Kein Polish**: keine Tests, keine Fehlerbehandlung über das Nötigste hinaus.
- **Zustand sichtbar machen** nach jeder Aktion bzw. bei jedem Varianten-Wechsel.

## Beispiel

Die Frage aus dem `handoff`-Dokument — bricht ein kritisches Event die stille Zeit? — ist eine Logik-Frage, kein Aussehen-Thema. Also der linke Zweig: eine HTML-Datei mit einem Schieberegler für "stille Zeit aktiv/inaktiv", einem Dropdown für Event-Kategorien und einem großen Log, das nach jedem Klick zeigt, was passiert wäre. Ein Produktmensch ohne Entwicklungshintergrund kann selbst durchklicken: *"Wenn ich 'Sicherheitswarnung' als kritisch markiere und die stille Zeit aktiv ist — kommt sie durch?"* Das Ergebnis (ja, aber nur wenn die Kategorie das explizit erlaubt) ist die Antwort, die per `handoff` zurück ins Hauptgespräch geht.

## Danach

Die validierte Entscheidung fließt in den echten Code ein — der Prototyp selbst wird als **Primärquelle** auf einem `prototype/<name>`-Branch aufbewahrt, referenziert vom Implementierungs-Issue.
